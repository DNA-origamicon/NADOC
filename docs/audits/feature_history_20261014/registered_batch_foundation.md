# Initial registered part batch foundation

This is a pure compiler/evaluator, without a public endpoint, session policy or
permission to publish. Assemblies remain deferred. The trust-policy plan remains
[automation_policy_plan.md](automation_policy_plan.md).

The strict version-1 envelope requires a Design ID/revision and 1–32 ordered
commands. The first catalog contains `helix-add`, `strand-add`, source-free gold
`nanoparticle-create/patch/delete`, `cluster_create` and `cluster_op`. Parameters
are separately reviewed public schemas, not a mirror of every replay contract.
No Python, full Design, geometry output, diff, recovery payload, source bytes,
generic sampled sweep or caller-supplied private proof/scope/generator field is
accepted. The existing bundle builder is excluded because it replaces the whole
Design and is not a general append operation preserving retained input tables.

Producer IDs are explicit typed canonical UUID declarations. The host supplies
a separate UUID namespace for stable feature/child/group IDs, allocated before
execution. Exact references resolve against the appropriate sequential state;
there is no recursive alias rewriting. Duplicate declarations and source identity
collisions fail before execution. Implicit native cluster collisions also fail.
The existing registry supplies the builders; no second geometry dispatcher or
recovery encoder was introduced.

Helix/strand additions form ordinary routing children. Gold steps remain ordinary
snapshot definitions. Cluster creation and pose remain their existing overlay
records. Group creation accepts unowned/default-owned whole helices and rejects
domain membership conflicts. Pose may address an existing domain-scoped cluster,
but changes no membership or ownership. Overlays reject arbitrary labels because
their native records use cluster display names and have no such label field.

Aggregate prospective work is bounded before any execution: 50,000 total helix
base pairs and separately 50,000 authored strand residues, including existing
source and all appended domains. Input JSON, 2,000 history entries and cumulative
8 MB recovery budgets remain unchanged. These are admission bounds, not measured
interactive qualification for the maximum batch. Source histories execute once
through `ReplayPrefix`; appended rows use the existing `regenerate` path and the
same recovery budget. Cancellation checkpoints propagate without publication.

Ready contains one complete candidate, ordinary row/output identifiers, source
assessment and a separate scientific validation report. It explicitly says
`candidate_replay_verified=False`: readiness alone is not independent cold proof
or an authenticated write capability. Tests rebuild mixed histories in spawned
workers after JSON transport, poison recovery data, edit ordinary child/overlay
inputs, and exercise failure, cancellation and work/identity boundaries.

Before public use, integrate existing bounded evaluation jobs and one atomic
expected-revision commit; bind server-owned policy generation and classify live
mutation/import/history paths. A server-owned verified baseline may eventually
avoid repeated source proof only with complete invalidation rules and trusted
receipt composition. JSON labels or caller-provided agent identity confer no
authority. A local process with unrestricted filesystem/process access remains
outside this application policy's protection.

The [Onshape features API](https://onshape-public.github.io/docs/api-adv/featureaccess/)
supports parameterized feature records, while
[SolidWorks macro features](https://help.solidworks.com/2020/english/api/sldworksapiprogguide/Macro_Features/Overview_of_Macro_Features.htm?id=1.3.35.0)
provide rebuildable custom behavior. These CAD systems also allow arbitrary
custom computation; NADOC's requirement for separately editable reviewed
construction steps is a product policy, not a universal CAD restriction.
