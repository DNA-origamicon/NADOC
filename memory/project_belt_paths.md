# Assembly Belt Paths (open belt between two pulleys)

**Phase 1 shipped 2026-06-01.** Sibling to [[project-gear-relations]] — reuses its model/route/UI patterns almost 1:1. Build plan: `~/.claude/plans/nadoc-has-the-ability-snug-brook.md`.

## What it does

"Assembly → Define Belt Path…" opens a right-sidebar panel. Each of two pulleys is defined by (1) a revolute mate (its `axis_origin`/`axis_direction` give the rotation axis) + (2) a **rim connector** on the rotating body. Pulley **radius** = perpendicular distance from the connector to the axis line; the connector also fixes belt contact phase. The open belt (external tangents, same spin sense) is previewed live as a glowing green tube and, on Create, persisted to the assembly. Listed/deleted in a "Belt Paths" sub-section below the Mates list.

**This phase is DISPLAY-ONLY.** No kinematic coupling, no part mating/animation — that's the deferred next phase the data model is built forward-compatible for (a future carried-part ref + travel param, added without changing pulley refs).

## Three-Layer Law

Like a GearRelation, a BeltPath is assembly-level display metadata. It only stores+validates state — **never writes into any embedded Design**. It carries no `current_value`, so it's static across configuration snapshots (no AssemblyConfigurationSnapshot change).

## Files

- **Model** (`backend/core/models.py`): `BeltPulley` (joint_id, side, instance_id, connector_label, + advisory cached radius/center_world/connector_world) + `BeltPath` (id, name, pulley_a, pulley_b, validator: distinct joints + finite ≥0 radius). `Assembly.belt_paths: List[BeltPath]`. New `SnapshotOpKind` literals `assembly-create-belt`/`assembly-delete-belt`. Serializes through `Assembly` → `.nass` save/load with **zero** save/load code change.
- **Routes** (`backend/api/assembly.py`, after the gear section): `POST /assembly/belt-paths` (feature-logged create), `PATCH …/{id}` (silent), `DELETE …/{id}` (logged). Request models `BeltPulleyRequest`/`CreateBeltPathRequest`/`PatchBeltPathRequest` use lowercase `list[float]` and need `model_rebuild()` (the module has `from __future__ import annotations`, so nested-model field annotations are lazy strings FastAPI can't resolve otherwise). Reuses `_resolve_gear_endpoint` for side resolution. Radius is **frontend-supplied/advisory** — backend does not recompute connector world positions.
- **Geometry** (`frontend/src/scene/belt_geometry.js`, pure/display): `pulleyCenterRadius(axisOrigin, axisDir, connector)` → closest point on axis + radius. `computeBeltPath(A, B)` → closed-loop `THREE.Vector3[]`. Plane normal = pulley A's axis (B's center projected into A's plane; console-warns when axes deviate >5°). External-tangent contact angle is **`psi = acos((rA−rB)/D)`** — NOT the build-plan's `asin`/`pi/2+alpha` (that was wrong; verified numerically: larger pulley wraps the MAJOR arc, smaller the minor). Guards coincident/degenerate/nested. Arcs sampled ~5.6°/step; tangents get a few interior samples so the closed CatmullRom tube doesn't bow.
- **Glow preview** (`frontend/src/scene/belt_preview_layer.js`): `createBeltPreviewLayer(scene)` → `{setPath, clear, dispose}`. Green additive `TubeGeometry` core + fatter low-opacity halo along a closed `CatmullRomCurve3`. Group named `beltPreview`.
- **Renderer hooks** (`frontend/src/scene/assembly_joint_renderer.js`): a two-phase **interactive picker**. `enterBeltDefineMode({onJointPick,onRimPick,onCancel})` + `beltSetPhase(phase, opts)` + `exitBeltDefineMode`/`setBeltPreview`/`getConnectorDataMap`/`enumerateRevoluteEndpoints` (last refactored out of `_populateGearSelects`). **'joint' phase**: a dedicated overlay group `beltJointMarkers` draws one green additive torus per revolute joint at its axis_origin, oriented in the rotation plane, at `RING_R*1.5` (≈1.77, "emphasized"); invisible CircleGeometry discs give forgiving hit-testing; clicking → `onJointPick(endpoint)`. **'rim' phase**: markers rebuilt un-emphasized (`RING_R`, picked joint excluded); rim connectors of the picked instance shown (`_setBeltConnectorVisibility`); a unit-circle `THREE.Line` (`beltRimCircle`) follows the mouse via `ringPlaneHit` (center=axis_origin, radius=|hit−origin|), transform-only (no geom churn); clicking a connector → `onRimPick(conn)`. Own overlay built so it sidesteps the selection-gated **instanced** joint indicators (`_useSharedJoints` defaults ON). Markers/circle/preview all disposed in `exitBeltDefineMode`/`dispose`.

Done → belt tube + enable button. Viewport picks fill dropdowns + advance; manual dropdown edits mirror it. **Edit mode**: `open(belt)` sets `_editId`, prefills the 4 dropdowns from the stored pulleys, flips the button to **"Apply"**; nothing is sent until Apply (`patchBeltPath`), so Cancel/Escape reverts cleanly. Modeled on `polymerize_panel.js`; mounts after `#assembly-panel`.

Selected rim connectors (`_beltSelConn.{a,b}`) stay **visible + green** across phases until the panel closes (`_refreshBeltConnectors`). ## Real-time coupling (drives like a gear)

A belt couples its two pulley joints with the **same machinery as [[project-gear-relations]]** — a belt is modelled as a gear-shaped edge: `ratio = r_a/r_b` (equal rim speed) with an open-belt direction (**same world rotational sense**). The current_value↔physical map is `s=+1` child side / `−1` parent side, and flips when the two joint axes oppose, so **`invert = (s_a·s_b·sign(axis_a·axis_b)) < 0`**. `BeltPath` gained `joint_a_anchor`/`joint_b_anchor`, snapshotted from current joint values at create AND re-captured on patch (so editing radius/pulleys never jumps).

- **Backend** (`backend/api/assembly.py`): `_belt_to_relation(belt, joint_by_id)` → a `GearRelation` (id `__belt__<id>`); `_coupling_relations(assembly, joint_by_id)` = `gear_relations + belt edges`; `_propagate_gear_relations_from` now iterates that combined list, so all three rotation paths (joint PATCH / instance gizmo / group transform) drive belts. No `/resolve` route.
- **Frontend**: `beltCouplingRelations(assembly)` in `belt_geometry.js` returns the same gear-shaped edges; folded into `kinematics_ticker.js` `_rebuildIfNeeded` (RPM spin + propagation) and `main.js` `_applyGearLiveForRevoluteDrag` (gizmo live-drag). Ring-drag relies on the debounced backend PATCH.
- **Direction is derived, not user-toggled** (open belt only). Verified: parallel same-dir axes + both child side → ratio 1.5, invert false; anti-parallel axis → invert true (same world sense). `tests/test_belt_paths.py` has 4 coupling tests (direction+ratio, bidirectional, anti-parallel sign-flip, anchor no-jump); e2e asserts rotating pulley A→1.0 drives B→1.5.

## Belt riders — attaching parts (Phase 1, static placement)

`BeltRider {id, belt_path_id, instance_id, connector_label, arc_param}` on `Assembly.belt_riders`. Phase 1 = **static placement only** (no riding motion yet). Routes (`backend/api/assembly.py`): `POST /assembly/belt-riders` (accepts an optional `transform` `{values:[16]}` applied directly to the instance — cargo parts are free, no FK/joint-sync this phase — plus stores the rider; feature-logged `assembly-create-belt-rider`) and `DELETE …/{id}` (`assembly-delete-belt-rider`). SnapshotOpKinds added. 5 backend tests.

- **Seating** (chosen convention: **point along the belt**): `seatTransform(Pc, Nc, beltPoint, tangent, planeNormal, instMat)` in `belt_geometry.js` builds a rotation aligning the connector normal → belt **tangent** (travel direction), belt-plane normal as up, then `D = T(beltPoint)·R·T(−Pc)` and returns `D·instMat`. Unit-verified: connector pos → belt point, normal → tangent exactly. Arc helpers `beltCurvePoints(belt, jointById)` + `nearestArcParam(points, worldPoint)` (closest point on the closed polyline → arcParam 0..1 + tangent).
- **Frontend attach mode** (`assembly_joint_renderer.js`): `enterAttachMode(beltId, {onAttach,onCancel,onSelect,onNeedConnector})`. Click a connector to **select it (highlighted green via `_refreshAttachConnColors`); click it again to deselect, or click another to change** — the selection persists until the user **clicks the belt path**, which finalizes (`_finishAttach` computes arcParam + seating transform → `onAttach` → `api.createBeltRider`). Belt click with no selection → `onNeedConnector`. Both entry points use the SAME finalize-on-belt-click flow: **Method A** = inline ⊕ button on the belt row; **Method B** = right-click the belt → context menu "Attach part to belt" (`pickBeltAt(e)` returns the belt id under the cursor; the clicked point is NOT used as the location — the user clicks the belt to place). `isAttachMode()` gates normal selection in main.js (same as belt mode). main.js `_attachPartToBelt(beltId)` force-shows the belt + toasts each step.
- **UI list** (`assembly_panel.js`): each belt row gets a collapsible **"Parts on path (n)"** sub-list (`_beltRidersExpanded` Set) showing `instance · arc%` rows with a detach ×. Callbacks `onAttachToBelt`/`onDeleteBeltRider`.
- **Polymerize along belt (DONE)**: an option in the Polymerize panel — seed = an existing belt rider; repeats it around the loop as N belt riders (clones of the seed instance) at evenly-spaced `arc_param = base + k/N`, all sharing the seed's `local_transform`+`ref_angle` so the chain rides together (no new kinematics — `applyBeltRiders` drives them). **Spacing auto from part size**: footprint = the seed instance's world-AABB (`assemblyRenderer.getInstanceCenters().size`) projected onto the belt **tangent** at the seed (x-col of `beltFrameAt`); auto count = `round(L/footprint)` (overridable). Geometry is frontend-side: `main.js` `_beltFillInfo`/`_polymerizeBelt` compute per-copy world transforms (`beltFrameAt(arc)·local`) and POST to backend `POST /assembly/polymerize-belt` (`polymerize_belt`), which just clones the seed instance (`model_copy(deep)`, name `"<seed> +k"`) + records `BeltRider`s, one feature-logged op (`assembly-polymerize-belt`). Panel (`polymerize_panel.js`): belt-rider entries in the seed dropdown (`beltrider:<id>`), belt mode hides direction/pattern, pre-fills the auto count. v1: single-instance riders, standalone (ungrouped) copies. Tests: `test_polymerize_belt_*` (backend) + `e2e/belt_polymerize.spec.js`. `__NADOC_DBG__.beltFillCount`/`polymerizeBelt` exposed.

- **Phase 2 (riders ride — DONE)**: a rider stores `ref_angle` (driver pulley angle at attach) + `local_transform` (16-float row-major part pose relative to the belt frame at the attach arc point). Live position is **drift-free, derived from the absolute pulley angle**: `liveArc = arc_param + (θ_a − ref_angle)·(ds/dθ)/L`, then `world = beltFrameAt(liveArc) · local_transform`. Helpers in `belt_geometry.js`: `beltLoopLength`, `beltFrameAt(points, arc, planeNormal)` (x=tangent, z=plane normal), `beltDriveScale(belt, jointById, points)` = `(axis_a × r_vec)·tangent` at an interior arc-A point (≈ ±r_a; **sign sets travel direction — verify visually**), `riderLiveArc`, and `applyBeltRiders(assembly, thetaOf, applyMat)`. Driven in three MUTUALLY-EXCLUSIVE places (mirrors the belt coupling): **ticker** `tick()` (RPM spin only — gated on `spun`, i.e. a joint was RPM-integrated this tick, so it uses the live `_shadow`), **main.js assembly subscription** (discrete ring/gizmo/group commits + load, θ from store — **skipped while any joint is actively RPM-spinning** so it doesn't fight the ticker), and **`_applyGearLiveForRevoluteDrag`** (live gizmo/group drag). **FLICKER FIX (critical):** the ticker MUST NOT drive riders every frame — `_shadow` holds a stale angle (preserved ~1s across rebuilds for in-flight patches; also written by `_propagateGearRelations`), so an unconditional rider update yanked the rider back to the stale/original position 60×/s while the store-driven path pushed it to the new one. Pulleys didn't flicker because coupling propagation is a self-consistent no-op when not spinning, but the rider update read `_shadow` directly. Regression: `e2e/belt_rider_flicker.spec.js` (samples 8× over 1.2s after a manual patch; asserts the rider stays moved, spread <0.1). Since both pulleys are belt-coupled, driving from pulley A's angle suffices. NO rider-transform persistence — recomputed live from the persisted θ_a + rider state. Unit-verified: rider moves Δθ·r_a along the loop (node). Backend stores `ref_angle`/`local_transform`; `seatTransform`+`beltFrameAt` give `local = F0⁻¹·M0` at attach.

## Gotchas

- **Tangent formula is `acos`, not `asin`.** The build plan had a sign error; the shipped code uses `psi = acos((rA−rB)/D)`. Verified numerically (arc spans + points-on-circles).
- **No existing pre-2026-06-01 .nass has 2 revolute mates** to test against — `workspace/belt_test.nass` was synthesized. User also has hand-made `Belt_gear_v1`/`Belt_drive_test1` belt-design files in the workspace.
- Radius/center are cached-advisory only; the source of truth is joint_id+side+connector_label. The frontend recomputes geometry live.
- **Rotation handles + angle-unwrap (teleport fix).** There were THREE ways to rotate a revolute pulley: the green joint ring (`beginRingDrag`), drag-the-body (`beginRevoluteDragForJoint`), and the **TransformControls gizmo** (the "blue ring", screen-space scaled — the only one usable on large pulleys; the world-space green ring at fixed RING_R=1.18nm is a dot at the center of a big pulley, and `pickJointRing` returns null, so it was effectively dead — left disabled). All three recovered the angle via `atan2` (±π) and **wrapped past half a turn**, jumping `current_value` by 2π — invisible for a spinning pulley but teleporting a belt rider ~half the loop (`2π·r_a/L`). Fixes: ring + body-drag handlers accumulate the shortest step (`lastAngle`/`accum`). **The gizmo (the path users actually hit) now**: (1) unwraps its live angle via a per-drag accumulator `_revoluteGizmoAngle` in `_applyGearLiveForRevoluteDrag` (covers instance AND group gizmo — both call it), and (2) **commits the rotation as the joint's `current_value` + `endpoint_side`** (`_revoluteGizmoCommitValue` → `patchAssemblyJoint`) instead of a transform the backend re-derives — for BOTH the instance gizmo `onCommit` and the group gizmo `onCommit`. **`endpoint_side` is CRITICAL** (Belt_test1 regression): that assembly authors one pulley "backward" — moving wheel = joint's **parent** (`instance_a`), fixed `Axle_test` = **child** (`instance_b`) — and the other pulley the normal way. `patch_joint` legacy always moves `instance_b`, so committing current_value without a side rotated the *fixed axle* and knocked it + the belt out of alignment. Frontend derives the side from `_movingSideSignForRevolute` (which body is in the moving set); backend `patch_joint` gained an `endpoint_side` param routing to `_apply_revolute_value_to_gear_endpoint` (moves the correct seed + FK + coupling). **But the form bites too:** the joint-edit form re-sends `current_value` (degrees-rounded, so it differs from the stored radians) when you toggle "use rotation limits", WITHOUT an endpoint_side → legacy path rotated the fixed axle. So `patch_joint` now **infers** the side when none is given: if `instance_b` is fixed and the parent isn't, use side 'a' — i.e. **never rotate a fixed child**, for ANY caller (form, gizmo, animation). Tests: `test_endpoint_aware_revolute_moves_parent_not_fixed_child` (explicit side) + `test_revolute_value_drive_never_moves_fixed_child_without_endpoint_side` (inferred, mimics the form's current_value+clear_limits). Backend `_sync_revolute_values_for_instances` also gained an unwrap-relative-to-old-value safety net (note: `patch_instance` clears `base_transform` after a transform commit, so transform-based multi-step accumulation doesn't work anyway — which is *why* committing via `current_value` is the right path).
- **Belt rider drive direction is `s_a·(axis_a×r_vec)·tangent`**, NOT a hardcoded sign: the pulley body rotates `s_a·current_value` (`s_a=+1` child side 'b', −1 parent 'a'), so the rim/belt direction flips with the side. A constant sign breaks when the belt is recreated on the other endpoint side.
- **Belt mode suppresses normal part selection.** `assemblyJointRenderer.isBeltMode()` gates `_onAssemblyClick` (early return) and `_onAssemblyPointerDown` (left-button early return) in `main.js`, so picking a rim connector doesn't box-select the part under it / start a ring-drag/lasso.
- **Markers + rim circle use `depthTest:false`** (renderOrder 998/999) so they stay visible through cylinder / hull-prism part reps instead of vanishing inside them.

## Why

Turns the assembly editor into a belt/pulley mechanism designer to complement gears. The next phase mates a part onto the belt and animates it traveling the path (couple the two pulley revolutes by their radius ratio, like a GearRelation with `ratio = rA/rB`).
