Welcome screen shows a spinning indicator on any design that has a running/preparing MD or oxDNA job, with an ETA tooltip on hover; launching a new job while one is busy pops a Continue/Cancel warning.

**Entry points**
- Backend: `backend/api/routes_jobs.py` → `GET /api/jobs/active` returns `{jobs, count, any_running}`. One cheap cross-engine scan (reconciles each job's status, reads ≤1 log per *running* job for ETA). Registered in `main.py` as `jobs_router`. **Covers ALL FIVE engines (2026-07-07):** MD + oxDNA (explicit blocks, with ETA) and LAMMPS + mrDNA + CanDo (one shared loop, `eta_seconds=None`). Resource-class tags: LAMMPS/CanDo=`cpu`, mrDNA(ARBD)=`gpu`; all three `execution_target="local"`. Pin: `tests/test_jobs_active_all_engines.py`. **Side effect (intended):** the concurrency guard now also blocks on busy LAMMPS/mrDNA/CanDo jobs of the same resource class (e.g. an MD/GPU launch warns if mrDNA is running; an oxDNA-CPU launch warns if LAMMPS/CanDo is running) — they genuinely contend.
- Frontend shared module: `frontend/src/ui/job_activity.js` — pure helpers (`activeJobForPath`, `jobActivityTooltip`, `pickBlockingJob`, `formatEta`, `normPath`) + `fetchActiveJobs()` (via `client.listActiveJobs`) + `confirmNoConcurrentJob({excludeJobId})`. Tested in `job_activity.test.js`.
- Welcome spinner: `library_panel.js` polls every 4 s (skips while `mount.offsetParent === null`), decorates each file row's `.lib-row-status` span in place (reuses global `.nadoc-spinner` CSS) so the animation never restarts.
- **Per-engine sidebar-header spinner (2026-07-07):** `frontend/src/ui/engine_activity_headers.js` (`initEngineActivityHeaders({fetchActiveJobs, intervalMs, doc})`) inserts one hidden `.nadoc-spinner` into each engine's Dynamics-tab section-header title (`{oxdna,lammps,mrdna,cando}-jobs-heading` + `md-jobs-panel-heading`, `data-engine-spinner="<engine>"`) once at init, then polls `/api/jobs/active` every 4 s (skips while `document.hidden`) and shows the spinner for each engine that has a running/preparing job. So a collapsed panel still tells you which engine is busy at a glance. Pure mapping = `runningEngines(activeJobs)→Set` in `job_activity.js`. Wired in `main.js` (one import + `initEngineActivityHeaders()` after the LAMMPS panel init). Pins: `engine_activity_headers.test.js` (DOM toggle) + `job_activity.test.js` runningEngines suite. Live-verified against a running MD job: md header spinner `hidden:false`, other four hidden, zero console errors. **CSS gotcha (fixed):** the `.nadoc-spinner` class sets `display:inline-block`, which outranks the UA `[hidden]{display:none}` rule — so toggling `hidden` had NO visual effect and ALL five spinners rendered. Fixed globally in `components.css` with `.nadoc-spinner[hidden]{display:none}` (jsdom doesn't apply the stylesheet, so the DOM-toggle unit test can't catch this — verify visibility via computed `display` in the running app).
- Guard wired into all 7 launch handlers: MD relax/start/production (`md_jobs_panel.js`), oxDNA relax/start/production/seed (`oxdna_jobs_panel.js`). `excludeJobId=_selectedId` on resume so a job never warns about itself.

**Design decisions**
- "Busy" = `running` or `preparing` only; `queued` does NOT count (waiting its turn, not consuming the machine).
- **Resource-class aware (2026-07-06).** The guard is NOT a blanket one-job-at-a-time lock — it keys off which resource a run actually holds so a CPU-only sim can run beside a GPU one (plenty of cores, one GPU). `/api/jobs/active` now tags every entry with `resource_class` ("gpu"/"cpu"): NAMD (local) is always `"gpu"`; oxDNA follows its `backend` field (`CUDA`→gpu, `CPU`→cpu). `pickBlockingJob(activeJobs, {excludeJobId, newJobUsesGpu})` only blocks on a busy LOCAL job of the SAME class (a GPU launch ignores a busy CPU job and vice versa; bare-string 2nd arg still supported for legacy). Missing `resource_class`→gpu (conservative). `confirmNoConcurrentJob({excludeJobId, usesGpu=true})` passes it through; MD keeps `usesGpu:true` by default; the oxDNA production/resume handlers derive `usesGpu` from the selected job's backend; seed→gpu (spawns NAMD). Pins: `job_activity.test.js` (isGpuJob, pickBlockingJob class cases), `tests/test_jobs_active_resource_class.py`.
- **GPU-busy CPU-fallback popup (2026-07-06).** New `confirmGpuLaunch({usesGpu, hasCpuAlternative, devices, excludeJobId}) → 'gpu'|'cpu'|'cancel'`. For a GPU-capable launch WITH a CPU alternative (oxDNA — its MD stages run on the `CPU` backend), when the GPU is already occupied (a NADOC GPU job OR an external VRAM holder via `gpuStatus`) it shows a **three-way** popup (`showChoice` primitive, new in `primitives/confirm.js`): "Run on GPU anyway" (danger/red), "Run on CPU instead" (success/green), "Cancel". No CPU alternative (NAMD) → two-way "continue anyway/cancel". CPU launch beside a lone GPU job → proceeds silently; CPU-vs-CPU → warns. The oxDNA **Relax (Run)** handler now calls `confirmGpuLaunch` in place of the old `confirmNoConcurrentJob`+`confirmGpuNotBusy` pair and sets `body.backend='CPU'` on the 'cpu' choice. Never blocks on its own detection errors. `showChoice` is size `md` (480px, wrapping actions) so the three labelled buttons don't clip. Pins: `job_activity.test.js` confirmGpuLaunch suite (three-way / external-GPU / dismiss→cancel / no-alt two-way / CPU-side-by-side). **NOT yet clicked in the running app** (owes an MV row + the in-app three-way-popup exercise).
- **Contention benchmark validates the premise (2026-07-06).** Measured CPU-oxDNA vs GPU-resident-NAMD side-by-side on this box (32 cores, 1× RTX; NAMD `+p16`, oxDNA CPU single-thread). Design: NAMD = 2hb_noT solvated (31,790 atoms, GPUresident 4fs), oxDNA = VoltronCore 16,152 nt DNA2 MD. Result: **NAMD 392.4→395.5 ns/day = 100.8% of solo (zero slowdown, within noise; GPU util held 96%)**; **oxDNA 32.93→28.68 steps/s = 87.1% of solo (−12.9%)**. Takeaway: a CPU sim costs the GPU job ~nothing; the CPU job pays a modest ~13% (NAMD's 16 busy-wait worker threads contend for memory bandwidth/cores) — an excellent trade for the "one GPU, many cores" case, and exactly why the guard now lets them coexist. Harness in scratchpad `cpu_gpu_bench/` (throwaway).
- **Remote (Alpine) jobs are NOT local contention (2026-07-06).** `/api/jobs/active` now tags every entry with `execution_target` (MD from the job; oxDNA always `"local"` — it has no remote backend). `pickBlockingJob` only counts LOCAL jobs (`isLocalJob` = target `"local"` or missing/legacy), so a job running on the Alpine cluster never blocks a local launch, and the welcome-row spinner still shows it (the design *is* simulating, just remotely). Vice versa: the MD panel's Relax handler reads `_currentRunTarget()` FIRST and skips all three local-resource guards (`confirmNoConcurrentJob`, `confirmGpuNotBusy`, `confirmDiskSpaceOk`) when the target is Alpine — a remote submit isn't gated by a local run, a local GPU hog, or local disk (its trajectory writes to cluster scratch). Alpine submit-via-review-card was already unguarded. Pins: `job_activity.test.js` (alpine-ignored / still-blocks-local / legacy-missing-target / `isLocalJob`), `tests/test_jobs_active_execution_target.py`. Verified live: an actual running Alpine job (`6hbx100_noT`) is tagged `execution_target:"alpine"` by the endpoint.
- ETA: oxDNA reuses `oxdna_runner.job_progress().eta_seconds`; MD is best-effort from the current segment's ns/day × conf fs/step over remaining steps, `null` when any ingredient missing (e.g. log hasn't printed yet).

**Test gotcha**: the guard adds an async hop before a launch proceeds; panel tests that pump a fixed number of microtasks needed a `flush()` loop (see the seed tests in `oxdna_jobs_panel.test.js`). Verified in-app via Playwright route-stubbing of `/api/jobs/active` (temp spec, removed). Related: [[project_md_job_system]], [[project_job_disk_usage]].
