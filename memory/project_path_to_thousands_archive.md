### Phase 7 — Shared-path feature parity, THEN flip the default   [DONE — 2026-05-20; flipped 2e540e0]

**Why this exists:** the shared renderer is fast but several per-instance features were never
ported — they no-op via `_SHARED_RENDERER_STUB_DEFAULTS` (return a safe default, one-time
`console.warn`, no crash). A blanket flag flip would silently regress these in normal flows.
User decision 2026-05-20: **port the stubs, then hard-flip** (chose this over threshold-auto-enable
and over hard-flip-now). Flip is the LAST step of this phase.

**Core architectural finding (2026-05-20) — this gates ALL of 7a/7c:** every stubbed feature
hangs off a *per-instance* `helixCtrl` (a real Three.js subtree positioned in world space) — that's
what `backboneEntries`, cluster capture/apply, overhang arrows (`getInstanceRenderData.group`), and
cluster-bead picking all read from. The shared path deliberately has NO per-instance group (one
shared `helixCtrl` per source, GPU-composed instance transforms) — that IS the memory/perf win. So
the stubs can't be "filled in" against the batch directly.

**Chosen strategy: (A) on-demand materialization of the ACTIVE instance.** When an instance is
selected/edited, build one real per-instance-path-style `helixCtrl` for just that ONE instance in
world space (overlay), and hide its slot in the shared batch (visibility texture → 0). Every
stubbed editing/inspection method then delegates to the materialized instance and reuses the
per-instance code unchanged. Cost is trivial (only one instance materialized at a time). Rejected
(B) reimplement-each-feature-against-the-batch: far more code, duplicates the per-instance logic,
no clear win since only one instance is ever active. Linkers (7b) are the exception — they connect
arbitrary parts, are few (per overhang-connection, not per-bp), and should be their own group,
independent of materialization. Photo mode (7d) applies to the whole scene, also outside the
materialize-active model — handle via the shared materials' patched shaders.

### O(N) cold-open ROOT CAUSE + FIX (2026-05-21) — it was NOT the indicators

Profiled N=500 load by elimination (black-box per-subsystem timing, then a Playwright
network-waterfall). Cold-open ~43 s = `assemblyRenderer.rebuild` (via `onRebuildComplete`). But in
ISOLATION every subsystem is fast: `/assembly/geometry` 0.9 s cold / 0.13 s parse (27.8 MB, deduped
to 1 source), `getAllConnectorFrames` 0.3 s, `_buildSource` 0.15 s (groups=1, dedup works), joint
indicators 0.3 s, sync subscriber block 1.5 s, overhang sprites OFF. **The waterfall found it: one
`GET /assembly/instances/{id}/design` per instance — all 500 — ~480 ms each, serialized on the
single-worker uvicorn ≈ 43 s.** Source: `cluster_panel.js setAssemblyMode()` looped every instance
firing `api.getInstanceDesign`. **FIX (`cluster_panel.js` only):** dedup by source key — fetch each
unique source's design ONCE, share across all same-source instances (same-source = identical cluster
list; already the shared-renderer's assumption). **Result: N=500 rebuild 43.5 s → 2.2 s; `/design`
requests 500 → 1.** Remaining ~2 s includes the cold *geometry* source-build (O(sources) per the
"Open perf gap", not O(N)). The `loadMs` column in the real-GPU table above (…20.5/47.8 s) was THIS
bug — re-measure.
2. **The mid (cylinder) tier is DEAD for full/beads rep — by design, but wrong at scale.** Bucketing
   ([assembly_renderer.js:4300-4303](frontend/src/scene/assembly_renderer.js#L4300-L4303)): for cap 0
   (full/beads) it's binary `pxSq>=farPxSq ? close : far` — `closePx` (60) is never read, mid is
   unreachable. So a full-rep part renders full bp until it's **8 px tall**, then jumps to billboard.
   Consequence: an N=200 full assembly framed at normal zoom (parts 8–72 px) draws ALL 200 at full bp
   = **0.5–3 fps**; only recovers (~48 fps) once parts shrink below 8 px (billboard). The cylinder
   middle ground that would save it is never used. **Fix: wire `closePx` into cap-0 as a 3-way
   (full≥closePx > mid≥farPx > far), and/or default assemblies to cylinders rep (cap 1 already
   buckets correctly).**
3. **Full bp detail (close) is viable only for ~1–10 simultaneously-near instances** (p5 9 @ N=20,
   3.6 @ 50, 0.5 @ 200). Fine as the "zoomed onto one part" rep; catastrophic as a many-parts bucket.
   far vs hull are perf-equivalent (both ~1.3k tris/inst) — choose by appearance, not speed.

**Verdict on the 2000@60 / 5000@30 targets:** NOT met today (cheap tiers ~50 fps @ 200, ~20 @ 500),
and the ceiling is the un-instanced indicators, not part geometry. Fixing finding #1 is the gate.
